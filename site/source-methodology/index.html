Source Methodology

How Anime Card Farm Wiki decides what appears on money and reference pages — and how we show disagreement instead of hiding it.

Primary surfaces (preferred)

  1. In-game redeem UI and Shop labels on a logged-in session.
  2. Roblox experience listing for place ID 125039473548047 (title, description, update text) checked on a named date.
  3. Official group/shout channels when they exist and are clearly owned by the creators — linked from official links when verified.

Secondary surfaces (Contested candidates)

  • Dated public code aggregators and reputable game press lists.
  • Player reports emailed with redeem outcomes.
  • Video proof only when the UI and timestamp are readable — cropped “trust me” clips stay weak.

What never becomes Active alone

  • An undated TikTok comment thread.
  • A Discord screenshot with no date and no UI.
  • A mirror site copying our older table without a new check.

Packs, cards, mutations, offline

These hubs prefer methods over fabricated stats. Payback uses cost ÷ income gained from your Shop. Mutation and offline pages teach what to observe in UI (labels, timers, whether income moved) rather than publishing a fake multiplier sheet.

Failure documentation

Codes pages keep a failure checklist (wrong experience, typo, already redeemed, expired, network). That checklist is part of methodology: a failed redeem is data, not embarrassment.

Change log habit

Material table changes should move with the Checked date. Cosmetic copy edits do not require pretending a new codes audit happened.

Contact for source disputes

hello@animecardfarm.wiki — include the row, your redeem result, and the zone. See also Editorial policy.

Limits

We cannot watch every private server or every region’s shop simultaneously. A Contested label is a feature when evidence splits — not a bug.

Worked example (pattern, not a live claim)

Suppose List A dated the same day shows code FOO as working, our redeem fails, and List B already marks FOO expired. The row becomes Contested or Expired based on how strong the primary redeem attempt was — not based on which list has prettier graphics. We document both sides when Contested.

Shop numbers as sources

For packs and upgrades, the Shop UI in your client is the primary source for costs. Our pages teach formulas; they may show example figures clearly marked as examples. When examples rot, mail us — that is a methodology bug we fix.

Reproducibility

Another editor should be able to repeat the redeem attempt and get the same label family (Active vs Contested vs Expired) on the same day. If only one private account can redeem a string, that is not a public Active claim.

External citations format

When we cite a public list, we prefer: publisher name, page title, and date observed. Undated citations are downgraded automatically.

Negative results are first-class

A failed redeem on the check date is evidence. Methodology that only keeps successes creates the fake “4 Active” tables we are trying to beat.

Timezone discipline

Checked stamps use Asia/Shanghai unless a citation carries its own offset. When comparing two public lists, convert both to the same zone before calling them “same day.” A UTC Saturday evening list is already Sunday in Shanghai — that mistake creates false Contested rows.

Hierarchy reminder

  1. Your client redeem / Shop UI.
  2. Official creator surfaces linked from official links.
  3. Dated reputable lists.
  4. Everything else (social undated) — at best Contested seed, never sole Active proof.

When hierarchy levels disagree, label the disagreement; do not average them into a fake certainty.
